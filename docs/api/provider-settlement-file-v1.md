# Provider settlement file contract v1

Status: Approved for Release 0.3 implementation  
Owner: Reconciliation contract; generated by the Provider Simulator  
Authority: Product Definition v1.7 REC-01 through REC-05; Technical Specification v1.7 §§10 and Appendix G; ADR-024 and ADR-027

## Purpose

This contract defines the only Provider settlement-file format accepted in Release 0.3. It is deterministic, synthetic, Tenant-scoped after authenticated upload, and suitable for streaming validation and Spring Batch ingestion. It is not a bank statement or a real payment-network format.

## Transport and file limits

- File format: UTF-8 CSV following RFC 4180 quoting rules.
- Header: required once, first row, exact spelling and order shown below.
- Maximum encoded size: 50 MiB.
- Maximum data rows: 100,000.
- Empty files, additional columns, missing columns, reordered columns, duplicate headers, invalid UTF-8, NUL bytes, and embedded executable content are rejected structurally.
- The complete raw object is hashed with SHA-256 before validation and stored immutably in S3-compatible storage.
- Upload requires an authenticated Reconciliation Analyst with Tenant-wide `settlement:upload` permission. Provider and Tenant are server-side route/authorization context, not trusted file fields.

## Exact header

```csv
providerBatchReference,settlementPeriodStart,settlementPeriodEnd,providerRecordKey,operationType,providerIdempotencyKey,providerReference,amount,currency,transactionStatus,settlementDate,providerEventTime
```

Every row in one file must use the same `providerBatchReference`, `settlementPeriodStart`, and `settlementPeriodEnd`.

## Field definitions

| Field | Required | Exact rule |
|---|---:|---|
| `providerBatchReference` | yes | 1-100 visible ASCII characters; stable Provider batch identity; no surrounding whitespace. |
| `settlementPeriodStart` | yes | ISO-8601 date `YYYY-MM-DD`; inclusive. |
| `settlementPeriodEnd` | yes | ISO-8601 date `YYYY-MM-DD`; inclusive; not before start. |
| `providerRecordKey` | yes | 1-120 visible ASCII characters; stable identity of one Provider settlement record/version family. Repeated keys remain separate physical occurrences for duplicate detection. |
| `operationType` | yes | Exact value `PAYMENT` or `REVERSAL`. |
| `providerIdempotencyKey` | yes | `payment:<lowercase-payment-uuid>` for Payment or `reversal:<lowercase-reversal-uuid>` for Reversal. It is the primary deterministic match key. |
| `providerReference` | yes | Stable Provider transaction/reference text, 1-120 visible characters. When internal evidence has a reference, both values must agree. |
| `amount` | yes | Positive decimal string in plain notation; no sign, exponent, grouping separator, or currency symbol; precision must equal or fit the currency’s ISO 4217 fraction digits. |
| `currency` | yes | Uppercase three-letter ISO 4217 code supported by the Tenant and matching the subject. |
| `transactionStatus` | yes | Exact value `SUCCESS`, `REVERSED`, `FAILED`, or `PENDING`. Unknown values invalidate the row. |
| `settlementDate` | yes | ISO-8601 date `YYYY-MM-DD`; must fall within the declared settlement period. |
| `providerEventTime` | yes | RFC 3339 UTC instant, canonical `...Z` form, used as Provider evidence time rather than import time. |

Whitespace is significant after CSV decoding. Values are validated exactly; the importer does not silently trim, case-fold, repair, or coerce malformed values.

## Batch identity and immutable versions

A `SettlementBatchFamily` is unique by:

```text
tenantId + providerId + providerBatchReference
+ settlementPeriodStart + settlementPeriodEnd
```

A `SettlementBatchVersion` is unique by:

```text
batchFamilyId + rawFileSha256
```

An exact duplicate upload returns the existing version and creates no second import. Changed bytes create a new immutable version linked to the family. Raw objects are never overwritten.

## Canonical record and physical occurrence identity

Ingestion preserves two identities:

```text
CanonicalSettlementRecordVersion:
tenantId + providerId + providerRecordKey + normalizedContentHash

SettlementRecordOccurrence:
tenantId + settlementBatchVersionId + rowNumber
```

The normalized content hash covers the exact semantic fields from `operationType` through `providerEventTime`, including the provider batch/period values, in the contract’s displayed order using canonical UTF-8 JSON.

This dual model is mandatory:

- unchanged content in a corrected file reuses the canonical record version and cannot create another settlement posting;
- every physical row remains an immutable occurrence, so duplicate keys, repeated rows, and conflicting content remain visible;
- two occurrences with the same key and same content are classified as duplicate Provider rows;
- within one batch version, the same key with different content is conflicting Provider evidence and is never silently replaced; across an explicitly superseding corrected batch version, changed content creates a new canonical version and follows ADR-024 current-run, Case, compensation, and replacement-posting controls.

## Matching rules

Matching is deterministic and never fuzzy.

1. Resolve the subject by `providerIdempotencyKey` and `operationType` through published Provider/Payment APIs.
2. Require Tenant ownership and the expected Provider (`SIMULATOR` in the baseline).
3. Require `providerReference` to equal durable Provider evidence when present.
4. Compare amount, currency, terminal status, and settlement date exactly.
5. Do not match by amount/date similarity, partial references, text similarity, or “closest” record.

Expected terminal settlement status:

| Operation | Required settled status | Additional prerequisite |
|---|---|---|
| Payment | `SUCCESS` | Payment is `COMPLETED` or `REVERSED` and has the exact ADR-020 posting. |
| Reversal | `REVERSED` | Reversal is `COMPLETED`, Payment is `REVERSED`, and the exact ADR-023 compensation exists. |

A syntactically valid but different status creates a `STATUS_MISMATCH`. `FAILED` or `PENDING` is not treated as successful settlement.

## Validation outcomes

Structural/file-identity failure rejects the complete file and imports no normalized records.

Row-level validation preserves a deterministic validation item with row number, reason code, and bounded safe evidence. Valid rows may proceed only after the analyst reviews the summary and explicitly confirms `READY -> PROCESSING`; invalid rows remain quarantined and produce `COMPLETED_WITH_DISCREPANCIES` when processing completes.

Closed row/file reason codes include:

```text
INVALID_HEADER
INVALID_UTF8
FILE_TOO_LARGE
TOO_MANY_ROWS
INCONSISTENT_BATCH_IDENTITY
INVALID_FIELD
UNSUPPORTED_CURRENCY
DUPLICATE_PROVIDER_RECORD
CONFLICTING_PROVIDER_RECORD
SUBJECT_NOT_FOUND
PROVIDER_REFERENCE_MISMATCH
AMOUNT_MISMATCH
CURRENCY_MISMATCH
STATUS_MISMATCH
SETTLEMENT_DATE_MISMATCH
```

## Settlement posting relationship

The file does not directly select Ledger accounts and never authorizes a posting.

Only a current immutable Reconciliation result may create a `SettlementPostingInstruction` keyed by the canonical settlement record version, matched subject, and template version. The instruction’s stable `settlementPostingId` becomes the Ledger source ID. Physical occurrences never create separate financial effects.

Payment settlement template:

```text
DEBIT  SETTLEMENT_RECEIVABLE
CREDIT PROVIDER_CLEARING
```

Reversal settlement template is the exact inverse and is allowed only when the corresponding uncompensated Payment settlement exists:

```text
DEBIT  PROVIDER_CLEARING
CREDIT SETTLEMENT_RECEIVABLE
```

Every posting follows ADR-024 locking, replay, current-run, and correction rules.

## Provider Simulator generation

The Provider Simulator uses the ADR-027 scenario snapshot pinned at the first Payment or Reversal attempt. `settlementMode` determines inclusion and deliberate mismatch scenarios. Generated files preserve stable Provider keys and deterministic ordering so the same scenario/seed produces byte-identical output.

Supported synthetic settlement fixtures/workflows include:

- normal matching record;
- missing Provider record;
- duplicate Provider row;
- amount mismatch;
- currency mismatch;
- status mismatch;
- settlement-date mismatch;
- corrected file version generated by an explicit superseding-file operation rather than a new ADR-027 `settlementMode`; and
- Reversal data setup with or without its required Payment-settlement prerequisite, used to verify ordering and discrepancy behavior.

## Security and observability

- File name and CSV text never establish Tenant identity.
- CSV values are data only; exports and inspection escape spreadsheet formula prefixes.
- Logs contain batch/version/row identifiers and reason codes, not complete file rows.
- Raw files are sandbox-only synthetic evidence.
- Object storage, database, and Spring Batch failures are recoverable through immutable hash identity and restart metadata.

## Verification

Implementation must prove:

- valid and invalid contract fixtures;
- exact duplicate and corrected-file concurrency;
- duplicate/conflicting physical row preservation;
- canonical-version reuse across corrected files;
- deterministic matching and closed discrepancy categories;
- 100,000-row bounded-memory processing;
- object-storage failure and database-failure recovery;
- Spring Batch crash/restart without duplicate normalized records;
- Tenant isolation and authorization;
- stable settlement posting identity across reruns; and
- no direct Reconciliation write to Payment or Ledger tables.
